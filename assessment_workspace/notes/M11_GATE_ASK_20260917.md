## Tension (a) — thin-kernel / no-refactor vs B.2 mandatory repository layer

**Statement**: SO §3.8 (thin-kernel / no-refactor · additive-only CPs · no existing-file rewrites) forbids modifying sealed M9 modules. B.2 mandates that every state-changing surface use `akki.data` repository primitives with auto-injected `{tenant_id: ctx.tenant_id}` filters and cross-tenant-write rejection. Wiring the 36 M9 shape refusers to real Mongo persistence requires either (i) modifying M9 modules (refactor · violates SO §3.8), or (ii) new wrapper modules (additive · doubles module count).

**Owner options**:

- **Option A · Additive wrapper (strict SO §3.8)**. Every M9 module gets a sibling `<module>_repo.py` wrapper that calls the M9 refuser first, then the repo. AST negative-scan enforces sole-importer. Doubles module count.
- **Option B · Narrow refactor exception under owner rule (amended SO §3.8)**. One-time milestone-scoped exception for M11: each M9 module gains one import + one `Depends(repo_factory)`. Cleaner but weakens SO §3.8.
- **Option C · Hybrid — thin adapter layer at `services/enforce/<entity>_gate.py`** (agent recommends). One adapter per M9 entity (~15 LOC). Imports M9 refuser + `akki.data.repo`. AST negative-scan enforces only `services/enforce/` may import both. SO §3.8 held verbatim; no M9 changes; adapters are one clean layer with its own gate.

**Agent recommendation**: **Option C** — matches chokepoint precedent, additive, testable.

## Tension (b) — zero closed enums vs B.8 determinism fixed enumerations

**Statement**: SO §3.10 (zero closed enum type in any M9 module) is verbatim in every M9 seal note. B.8 mandates byte-identical golden-input determinism tests for TCB components. Some TCB components genuinely have finite closed enumerations (Watch verdict actions: destroy·sever·contain·monitor; permission verbs: read·write·admin·dangerous; 12 capability ceilings). Determinism harnesses need the closed set enumerated authoritatively.

**Observation from disk**: closed enumerations ALREADY exist as `tuple[str]` module constants (`ACTION_CLASSES`, `PILOT_TENANT_KEYS = ("RMS", "DigiCow", "BDO", "Trinity")`) without using `enum.Enum`. SO §3.10 as authored may already ban only `enum.Enum` (technical reading), not fixed-vocabulary tuples (semantic reading).

**Owner options**:

- **Option α · Clarify SO §3.10 as technical** (agent recommends). "Zero closed enum type" means zero `from enum import Enum` or subclassing `Enum` / `IntEnum` / `str, Enum`. Fixed-vocabulary `tuple[str, ...]` module-level constants are ALLOWED. No M9 rework. Requires SO §3.10 amendment note.
- **Option β · Ban tuples too; every closed set is a JSON config**. Every finite enumeration lives in a `.v0.json` file (existing precedent: `masking_tier_allowlist.v0.json`). High rework impact.
- **Option γ · Delete SO §3.10 entirely**. Loses discipline benefit. Not recommended.

**Agent recommendation**: **Option α** — codifies existing on-disk practice, amends SO §3.10 to specify "no `enum.Enum` subclass", preserves OPEN-`str`-carrier discipline while unblocking B.8 harnesses.
