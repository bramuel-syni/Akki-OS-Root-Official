- **Class-distinctness argument**: Repository provides the GENERIC leaf-primitive delete op for the multi-tenant data plane (auto-injects `tenant_id`, refuses AKKI-DATA-001 on cross-tenant). `authorized_deletion.py` encodes RETENTION POLICY on held classes (ledger_row, wizard_transcript, delivered_artifact). A future refactor may route `authorized_deletion.execute_authorized_deletion` THROUGH Repository (so retention policy composes with the leaf primitive), landing in a later M11 wave (W6-W7 · retention TTL).
- **SO §3.8 status**: **HELD** — this is a WHITELIST EXTENSION (parameterisation of existing enforcement logic), not a refactor of the invariant's assertion body. Precedent-anchored to R-A-2 extension.

### Option B · Route Repository's delete methods through authorized_deletion
- **Action**: Repository's `delete_one` / `delete_many` methods delegate to a new function `authorized_deletion.execute_repository_delete(coll, filter, mode='one'|'many')` which owns the concrete `collection.delete_one/many` call site. Repository does auto-inject-tenant + refuse-cross-tenant; then hands off.
- **Class-inversion problem**: This makes `services/data/repository.py` (leaf primitive) depend on `services/retention/authorized_deletion.py` (governance surface). Inverts the layering — the leaf now imports the governance module, which will bind Repository to the specific held_class registry semantics of authorized_deletion.py. Not clean.
- **Also**: `authorized_deletion.py` currently has direct `db[collection_name].delete_many(selector)` on line 119 — those are inside the retention module and pass the whitelist. But making it a generic delete surface pulls Repository's caller-supplied `filter` into a module that was scoped to retention semantics. Feels like a category error.
- **SO §3.8 status**: modifies both `services/retention/authorized_deletion.py` AND `services/data/repository.py` at land — needs owner ruling to amend §3.8.
- **Ratchet impact**: potentially +new tests to enforce the delegation.
- **Not recommended** (architectural inversion).

### Option C · Repository owns no delete methods; deletions route through `services/retention/authorized_deletion.py` exclusively
