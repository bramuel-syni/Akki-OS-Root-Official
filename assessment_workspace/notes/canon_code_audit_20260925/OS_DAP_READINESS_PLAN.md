## Readiness definition proposed for this plan

Akki OS: the estate team can connect an authorized source, commission bounded work, inspect actual execution, exercise required approvals/stop/retry controls, and retrieve a result with its governing records.

DAP: an admitted party can see only the permitted estate view, submit a request under real terms, receive approval/refusal where required, obtain the permitted result, and see accurate history and metering.

Both surfaces must use the same underlying owned records and executor state, not separate imitation workflows. Every enabled action must perform the advertised operation. Optional capabilities may remain explicitly unavailable only where the Canon permits that posture. A functioning limited operational release is not a full-Canon conformance certificate.

## Non-negotiable working constraints

- Preserve the existing engine boundaries, single-writer authority per record class, and extension-not-sibling architecture.
- The E1 pod never becomes an estate-data path or training host. Wire descriptors and execution contracts; Akki performs the work within its perimeter.
- No fabricated totals, allowances, detector scores, progress or completion. Missing measurement is not zero measurement.
- Owner/rule-defined rights, budgets and acceptance criteria are not invented or silently relaxed.
- No speculative GPU password/key changes. Use Akki's own evidence and approved recovery pipeline only if required.
- Bank each change, refusal, verification and acceptance receipt in the assessment workspace and appropriate owning record system.

## Phase 6 — operational acceptance and handover (P0 release gate)

Required acceptance pack:
- Source-aligned regression tests and browser journeys for both OS and DAP.
- Refusal tests for unauthorized scope, missing approval/terms, unavailable source, exhausted budget, unavailable model, below-floor result and failed mandatory receipt writing.
- Worker interruption, restart recovery, cancellation, bounded retries, idempotency and durable-state checks.
- Validated restore/recovery procedures for each governing store, with declared ownership and retention.
- Current component/configuration inventory, operator diagnostics, actionable failures and operational runbook. No secret values in the acceptance report.
- Real artifact/result/receipt evidence for the declared scope; no demonstration data passed off as operational results.
- Owner walkthrough of the complete OS and DAP journeys and a list of explicitly excluded optional capabilities.

Exit evidence: a bounded acceptance record states the exact workflows and version verified, remaining exclusions, and named acceptance. No whole-platform “ready” claim based solely on service health, route count, screenshots or old test receipts.

## Delivery order and parallel work

Order: evidence map → shared identity/record boundaries → real census/registry → one request-to-result vertical slice → OS and DAP surface completion in parallel → skills/training for enabled services → operational acceptance.

The first implementation milestone should prove **DAP request → same OS work item → Akki executor → verified result/receipt → DAP history**, backed by the real authorized census inventory. It should not be a broad rewrite of all service directories or another dashboard.

No calendar or cost estimate is represented as reliable yet. Size work after Phase 0 exposes the untraced paths and the necessary corpus/evaluation scope; execution is then planned in small, independently accepted batches.

## Backlog distinct from initial operational acceptance

Deeper estate-wide quality/FK/dedup measurement, additional analytical/learned capabilities, and broader research/optimization may follow only where the Canon and the agreed operating scope permit deferral. Mandatory governance, receipt, custody and truthfulness requirements cannot be put into backlog merely to obtain a readiness label.

Useful improvement: keep measured/estimated/not-read status and freshness visible beside existing registry figures, deriving from the same receipts instead of another summary store.
