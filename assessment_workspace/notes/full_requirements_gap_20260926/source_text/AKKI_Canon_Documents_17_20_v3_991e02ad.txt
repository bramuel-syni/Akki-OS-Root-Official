[B5] DOCUMENT 17   The Multidimensional Training Engine

[B6] The Multidimensional Training Engine

[B7] Extends and completes Promises #22, #23, #24 (Documents 13–14). Its audio-specific depth is reused directly from the Audio Intelligence Plane Specification v1.0 (RMS-IQ-Core-2, docs/mandates/akki_os_pack_v1/ — supplied by the Owner 2026-07-30, the ninth and final document of the AkkiOS pack, explicitly “the single reference for build”) — not generalised away from, as an earlier version of this document incorrectly did.

[B8] 17.1 · The promise, in plain language

[B9] Given governed access to an audio estate, the platform provides four functions in one loop, not one: Extraction converts audio into provenance-paired facts; Learning accumulates group-level knowledge of how the estate's languages and audio behave; Training commissions model production against a falsifiable target, planned and priced before compute is spent; Invention constructs synthesized voice identities from what's been learned — authentically of the language, provably of no individual. Each function feeds the next: extraction populates the register that training plans against; trained models improve extraction; invention consumes the register's learned layers. This is Promise #22 and #23's own language (“the platform trains models on its own … meeting every criterion on uncurated held-out material or not entering service”; “before committing a training job, the platform works with the user to get the objective right”), extended by the two functions — Learning and Invention — that the source documents named but that never landed in this canon until now.

[B10] 17.2 · The service that powers it

[B11] No sibling services. Per the source's own governing doctrine (§1.2): Mtafiti gains an audio modality and the Character Register; Northena gains audio data classes on its one ledger; the shaping wizard gains an Objective Wizard variant; Targeta gains a training object and a third planning mode. Anything that reads as a parallel to an existing service is rule proliferation and must be collapsed into the existing service before build — stated as a standing principle, not a one-time note.

[B12] 17.3 · Definition of the promise

[B13] Five principles govern every clause below. Where any clause conflicts with one of these, the principle wins and the clause is defective — the source's own words, reused because the standard is worth inheriting exactly.

[B14] An audio file is a data estate, and the framing is recursive. The archive is an estate; a programme is an estate; a single file is an estate. Segments are rows; content, language, condition, prosody, occurrence, code-switch, music, and group-level character are columns — no schema exists until one is declared. Census, admission, registry, and record apply at every scale.

[B15] Modality extension, not parallel machinery (§17.2).

[B16] One record. Mtafiti and Northena collaborate to produce a single record, written once. Working state — loss curves, intermediate metrics, partial coverage counts — is scratch, not truth, until finalized and stamped. No local ledger exists anywhere in this design. If a measured throughput ceiling ever demands relief, the relief is batched stamping — one row certifying N events with a digest — which remains a single record; that change is made only when a measurement demands it, never pre-emptively.

[B17] Measure, do not assert. No data-volume requirement, accuracy expectation, or cost figure is quoted without a measurement behind it — calibration exists specifically to convert assertions into measurements before commitment.

[B18] Unrepresentable, not policed. Safety boundaries are enforced by making the violating state impossible to express in the contract, not by review after the fact — the pattern already proven for the assertion floor (Document 4), applied here to the Character Register's write path (§17.5) and the voice identity distance gate (§17.5).

[B19] The end-to-end commission flow these principles produce: an Objective Wizard session compiles a TargetOutcome and a Collection Schema → Sampling & Reflection (calibration) produces proposed milestones and a priced quote → the owner agrees the milestones and the commission opens → collection updates the register, which drives the curriculum, which drives training runs, which produce certificates → the Commission View reports against milestones throughout → the commission seals.

[B20] Foundation method is fixed, not chosen per run

[B21] Every model the platform trains is a LoRA/PEFT adapter over a registered open base model — never a full fine-tune, never an unregistered model. This is FACT-class in the ratified Training Techniques Spec, meaning it is not revisited per training job; it is a standing constraint on what “training” is allowed to mean on this platform. Training material is drawn exclusively from de-duplicated, qualified units — the same units the estate's extraction pipeline already produces, never raw source reached around that pipeline. Acceptance runs exclusively through MOAC on uncurated held-out sets: a model is never accepted on the material it was tuned against.

[B22] Configuration is a governed object, not code

[B23] If the optimizer, the learning-rate schedule, the batch and epoch parameters, and the adapter's rank and target modules lived in code, every change to how a model trains would be a code change — reviewed on a different cadence, by different people, invisible to the ledger that governs every other consequential object on the platform. Instead, all of it lives under training_params@v0, a sidecar configuration class carrying the identical discipline already proven for extraction_params@v0: versioned, ledgered, kept outside contracts/, with no Parity contact.

[B24] The seat starts empty; evidence fills it, not judgement

[B25] No default recipe exists at commission. The first real training run does not consume a pre-set configuration — it is the mechanism that produces one, through the measured optimizer-selection protocol (§17.5). Every trained model's registry entry cites the exact recipe_version that produced it, extending MOAC's lineage criterion (M-d) by this field.

[B26] 17.4a · Extraction — audio into provenance-paired facts

[B27] Everything below sits ahead of the Character Register and training in the loop; it is where the register's raw material comes from, and none of it is generic — it is specific to audio and was entirely absent from this document until now.

[B28] Tokenized representation

[B29] All downstream audio work — extraction, character analysis, training — operates on discrete token sequences from a neural audio codec, never on waveforms directly. Tokenization exposes two separable streams per segment: the content stream (what was said, feeding ASR/NER) and the character stream (how it was said, feeding the Character Register) — the character stream is retained and routed, never discarded as noise. Control markers for language, register, and segment type are splice-able tokens, enabling one model per estate rather than one per language, with native handling of code-switched speech. Audio in an unsupported condition fails closed with a stated reason; the codec never silently degrades quality. The service (perception/audio_codec/) is registered like any other perception model, census-visible, running in-perimeter on tenant compute; codec_version is a mandatory field of every downstream artifact's provenance, and round-trip fidelity is measured and recorded per codec version before that version serves any commission. Codec choice itself — adopt an existing open codec or train one estate-specific — was an open question in the source spec; it is now ruled DELEGATED-REVERSIBLE (§17.5 rulings), a config slot the builder sets initially and Sampling & Reflection re-derives on evidence.

[B30] Language identification and code-switching

[B31] Every segment carries a real language signal — the current plumbing value of language_hint: None is retired. A lightweight, offline, CPU-viable identifier runs at segment level during ingestion, recording languages, confidences, and code-switch points where multiple languages occur in one utterance; the signal routes downstream model selection and is written into provenance. Switch points — position, from-language, to-language, context class — are registered facts with provenance, not preprocessing metadata: they populate the register's code-switch layer and stratify test sets directly.

[B32] Condition profiling and synthesis-attribute capture

[B33] Channel condition — studio, field, or telephone band, transmission artefacts, background class — is derived per segment at first ingestion, because it is cheap to compute, directly predictive of extraction error, and required for training stratification; re-ingesting an estate to recover it later is the mistake this captures against. In the same ingestion pass, group-level acoustic attributes any future synthesis capability will need — pitch statistics, energy contours, duration patterns — are captured subject to the custody conditions below (§17.4b); this forecloses nothing and costs little, while omitting it forecloses invention entirely or forces a full re-ingestion.

[B34] Deduplication as augmentation

[B35] The existing occurrence index's output contract extends: for each deduplicated item, the instance condition map — the set of channel, time, and condition variants under which identical content occurred — is retained. One canonical extraction is stored; the variant set enters training curricula as a designated robustness stratum at zero acquisition cost. No new detection work — this changes only what dedup keeps.

[B36] 17.4b · Learning — the Character Register and its custody boundary

[B37] This is the function most completely missing from every prior version of this document. It is not an extraction detail; it is a second learning capability with its own governance model, sitting alongside the extraction pipeline and feeding the training planner.

[B38] Definition and layers

[B39] A registry-modality store of learned, group-level audio characteristics, built from the character stream — Mtafiti's existing qualification-and-index doctrine applied to acoustic observations, an extension per §17.2, not a sibling. Every entry carries provenance to source material and an occurrence count, across four layers: phonetic (per-lexeme pronunciation variants, frequency, regional distribution — feeding curricula, extraction lexicons, and evaluation stratification); prosodic (intonation, stress, rate, pause structure — feeding training and programme-type classification); condition (channel and environment profiles — feeding stratification and error prediction); and code-switch (switch-point patterns, language pairs, context classes — feeding training and test-set design). Built by unsupervised clustering over the character stream, which yields candidate strata — a cluster asserts that a distinct variant exists, not what it is called; naming and validation are human work applied to a sample, commissioned and priced like any other qualified work.

[B40] The custody boundary: organic versus learned

[B41] Organic characteristics are anatomical — vocal tract length, formant structure, glottal source, fundamental-frequency range. They cannot be acquired or shed; they are exactly what speaker verification keys on; they are biometric. They are never registered. Learned characteristics are acquired from a speech community — phonological inventory, pronunciation variants, prosody, code-switching habits — group properties by construction. Only learned characteristics may be registered, and only if all four conditions hold simultaneously: acquired, not anatomical (learnable by a speaker from a different background); shared (observed across at least N distinct speakers, N a governed seam value defaulting to the platform's minimum-group-size parameter unless a tenant sets a register-specific value — open decision, §17.5); non-reconstructive in combination (tested against attribute combinations, not attributes alone — language + region + age band + one distinctive feature can reach a single person even when every attribute is group-level); and stored as description, not exemplar (centroids and distributions only — never stored audio, never per-utterance speaker embeddings; embeddings used during clustering are destroyed after cluster assignment, and provenance points to material, not to speaker identity). Habitual fillers and idiosyncratic pronunciations are learned but individuating — they fail condition three or four and are excluded; “learned” alone is never sufficient, the four conditions are conjunctive.

[B42] Enforcement: unrepresentable, not policed

[B43] The register's write path exposes no field through which an instance-level representation can be stored — the schema itself cannot represent a voiceprint. An automated invariant test attempts each known leakage path (a small stratum, an idiolect marker, a narrowing attribute combination, exemplar storage) on every change to the register code, and must fail to store all of them. This is the same enforcement pattern Document 1 uses for its chokepoint, applied here to a second boundary that governs what may be learned rather than what may leave.

[B44] 17.4c · Invention — synthesized voice identity

[B45] A real, specified, sellable capability, and a second component entirely missing until now.

[B46] Mechanism: inherit the learned, synthesize the organic

[B47] Learned characteristics are inherited from the register — this is what makes a constructed voice sound like a genuine speaker of the language rather than a foreigner reading it. Organic characteristics are constructed: vocal-tract parameters, F0 range, formant structure, and glottal parameters are chosen as a point in acoustic space that no real speaker occupies. This is the inverse of a voice clone — a clone copies the organic and frequently gets the learned wrong; this gets the learned right and owns the organic outright.

[B48] The distance guarantee — mandatory, fail-closed

[B49] Every constructed identity is scored against every speaker representation derivable from the corpus, using standard speaker-verification methods, and a minimum distance from all of them is required. Below threshold, the identity is rejected and resampled. There is no override. The threshold value and the verification method are recorded permanently with the identity.

[B50] The certificate — a sellable artifact, not a byproduct

[B51] A passing identity is issued a certificate stating that the voice is provably derived from no individual, naming the method, the threshold, and the corpus version scored against. Synthetic voice is currently a legal hazard for any broadcaster or brand that touches it, and the hazard is provenance, not technical quality — nobody can normally prove whose voice it is not. An artefact that proves absence of derivation is the product, sellable on its own terms. Identity composition: acoustic identity from constructed organic parameters; speech character inherited from the register's phonetic and prosodic layers; interaction character — turn-taking, formality, code-switch behaviour — also inherited from the register. Each identity is a versioned artefact with a ledger entry; changing one is a ceremony with the standard waiting period, because audience recognition accrues to the voice and that recognition is the asset. Identities never drift.

[B52] Scope, stated honestly

[B53] Rendering requires a synthesis stack — a separate build from recognition, explicitly Phase 2. What this specification requires now is non-foreclosure: the identity specification, the distance method, and the certificate format are defined, and the ingestion capture in §17.4a ensures the substrate exists when rendering is eventually built. Say that the specification is defined and the substrate is guaranteed; do not imply that rendering ships today.

[B54] 17.4d · The commission chain — two compiled artifacts, not one

[B55] Corrects a real gap: the wizard compiles two governed artifacts, and only one of them was in any prior version of this document.

[B56] The Objective Wizard as schema compiler

[B57] No business user hand-writes a Target Outcome. The Objective Wizard — a variant of the existing shaping wizard, reusing its agent interface, guards, session persistence, and ledger sidecar — elicits an objective in plain language and compiles two artifacts: the TargetOutcome (§17.4e) handed to the Training Planner, and the Collection Schema (§17.4f) — the data dictionary for this objective, stating which data points are extracted from the sound, at what granularity, at what quality bar. Elicitation runs in four moves: the operational, falsifiable question the model must answer; the population, resolved against existing register strata (an unresolved population is flagged unmeasured and generates census work rather than being guessed); the acceptance bar per stratum, with the gate-or-document decision recorded explicitly; and the collection consequences — the wizard derives required columns, shows which are already collected, which exist but are uncollected, and what collecting them costs, so the owner sees the schema's price before commissioning.

[B58] Dynamism within scope: propose, qualify, graduate

[B59] The agent side may propose novel data points no prior objective collected — this is where innovation enters. A proposed column never enters collection directly: it is admitted as a candidate, collected on a sample only, its evidence of value measured against the objective, the same qualification path any fact travels. Qualified candidates graduate into the objective tier for that commission; graduation into the baseline tier is ceremony-governed (proposal, countersignature, waiting period), because a baseline column is paid on every hour ingested for the life of the estate. The compile stage is deterministic throughout — the agent proposes, only qualified columns compile — and mechanical guards prove against a stub agent before any LLM is plugged in. Rejected at compile, not warned: an Outcome without an existing test_set_ref; an acceptance bar missing its per-stratum dimension; a Collection Schema requiring a column whose capture would violate the custody conditions of §17.4b. Every session stamps to the ledger under its own data class, including options considered and rejected — which is what makes a later “why was the model built this way” answerable.

[B60] 17.4e · The Collection Schema

[B61] The declared data dictionary of a commission — what is extracted from the sound, for what purpose, at what quality bar — the admission standard of the audio estate, per objective. Two tiers: the baseline tier is standing and objective-independent, collected at first ingestion for all admitted material, membership decided purely by “cheap to collect now, unaffordable to collect later” — language ID, code-switch points, condition profile, the dedup instance condition map, and synthesis-relevant group-level acoustics at v1.0. Changes to the baseline are seam-governed (ceremony, countersignature, waiting period), because silently narrowing it is how an estate quietly becomes unre-readable. The objective tier is declared per commission by the Objective Wizard, collected against material already in governed scope, priced before collection starts, and recorded in the commission's own registry namespace; candidate columns enter only through propose–qualify–graduate (§17.4d).

[B62] Revision is cheap; unevidenced revision is a defect

[B63] Recipe revisions carry no approval ceremony — they are DEFAULT-class, expected to happen as evidence accumulates. But every revision must attach the measured comparison that justifies it and must write a ledger row. The absence of ceremony is not the absence of accountability: a revision with no attached evidence is not a lighter-weight change, it is a defect, indistinguishable in the record from an engineer overriding the platform's own evidentiary standard by hand.

[B64] The Target Outcome — training cannot be commissioned against an unfalsifiable goal

[B65] A training job is not admitted from a task description alone. It is admitted from a Target Outcome, a schema that forces the goal into a form that can actually fail:

[B66] TargetOutcome:

[B67] task            operational statement of what the model must do

[B68] domain          context of use

[B69] population      defined by reference to register strata, not labels

[B70] acceptance      threshold per stratum — two-dimensional (accuracy, coverage)

[B71] gate_policy     missed stratum gates release | ships documented

[B72] test_set_ref    must exist before the plan is accepted

[B73] constraints     latency, compute budget, deployment target

[B74] Two rules are binding, not advisory. Population is register-defined: “language L, accent clusters 1–4, telephone band and studio, adult”, never “speakers of L” — because only a register-defined population makes coverage a computable number rather than a felt impression. Acceptance is per stratum, not global: a single aggregate figure hides exactly the failure that matters — 94% on the majority variant and 61% on everything else passes one test and fails the one that decides whether the work reaches the people it was built for. Whether a missed stratum blocks release is a governed decision recorded on the Outcome at definition time, not an ad-hoc call made under ship-date pressure. And the ordering constraint is absolute: the test set precedes the training. An Outcome submitted without an existing, stratified test set is rejected at definition, before a single GPU-hour is spent.

[B75] The Training Planner — the same pattern as extraction, a different object and floor

[B76] The planner is not new architecture. It reuses, unchanged, the pattern already proven for extraction planning: a deterministic core computes eligibility; a learned layer may only reorder an already-eligible set, and it receives that set stripped of the values that decided eligibility in the first place, so it cannot learn to game the floor; a gate compares the learned layer's output against the deterministic baseline before anything ships; every plan is reproducible from its own recorded inputs. What changes between the two is only the object being planned over and the floor that governs it:

[B77R1]  | Extraction planning (existing) | Training planning (new)

[B77R2] Object | Source locations | Register strata

[B77R3] Floor | Defensibility class | Acceptance threshold — accuracy × coverage

[B77R4] Output | Mining plan | Training plan + curriculum + milestones

[B78] Planner outputs, per commissioned Outcome, are four things: a coverage report per target stratum — hours available, quality distribution, gaps, and the cost of closing each gap; a curriculum, ordered and weighted from the register itself, deliberately not from the corpus's natural distribution, which is always skewed toward whatever occurred most — the dedup instance-condition map enters here as a designated robustness stratum, at zero additional acquisition cost; the calibration commission (below); and a cost quote carrying a stated confidence interval, never a bare point estimate.

[B79] Calibration is the planner's mandatory first stage, not an optional safeguard. Data requirements for low-resource fine-tuning are empirical — no analytical formula predicts how much data a given stratum needs to cross its acceptance threshold. So the first commissioned job is never the real job: it trains at three or four data volumes, evaluates against the test set per stratum, fits the scaling curve, and only then extrapolates to what the full run would cost and how likely it is to clear the threshold. A plan without a calibration stage is rejected outright — the first job's entire purpose is to price the real one honestly.

[B80] Calibration has a second customer beyond pricing: it authors the accountability structure the objective owner will be held to. Its output is not only a curve, it is a proposed milestone list — the checklist of what must be done, in what order, for the commission to succeed, each milestone carrying a done-condition and an owner. The objective owner reviews and agrees this list at commission, before spend begins; every status report afterward is measured against it. Accountability is set before the money moves, not reconstructed afterward from whatever happened to get done.

[B81] Provenance survives the training, not just the extraction. Every training example carries its provenance into the training manifest, which has three consequences that matter beyond bookkeeping: rights are enforceable per example, so an example whose rights lapse is identifiable and every model it touched is enumerable, not merely suspected; “the trained model is the customer's property” becomes a defensible statement backed by a manifest rather than an assertion made because it sounds right; and the dedup instance-condition map enters the curriculum as a designated robustness stratum at zero acquisition cost, because it was already being computed for a different purpose.

[B82] 17.4 · Delivery experience expectations

[B83] What the organisation experiences (human-facing)

[B84] Defines a target outcome — task, domain, register-defined population, per-stratum acceptance — and the platform rejects it outright if the test set doesn't already exist.

[B85] Watches the mandatory first stage, calibration, as staged progress: three to four data volumes trained and evaluated per stratum, the scaling curve fit, the full run quoted only after — with a confidence interval, never a point estimate.

[B86] Receives the calibration run's second output alongside the price: a proposed milestone list, each with a done-condition and an owner, agreed before spend rather than discovered during it.

[B87] Sees an optimizer or recipe-component candidate proven or rejected by a measured two-arm comparison against the current baseline — both arms' numbers reported, parity mandatory for adoption, the verdict an Owner ruling on evidence rather than a preset threshold.

[B88] Gets a model that provably cleared all six MOAC criteria, or a recorded rejection with its numbers — never a manually waved-through model — with rejected candidates kept on the shelf permanently.

[B89] What a consuming system experiences (machine-facing)

[B90] Reads a model's registry entry citing its recipe_version, base model, and the rights lineage that trained it — lineage is enumerable, not asserted.

[B91] Reads a training run's completion certificate: compute consumed, data touched, manifest hash, and per-stratum results against the Outcome — failed strata reported as plainly as passed ones.

[B92] What is produced and retained

[B93] The training manifest — every example's provenance carried through to the trained artifact, so a lapsed-rights example is identifiable and every model it touched is enumerable.

[B94] The completion certificate and the recipe_version record, both permanent.

[B95] On rejection, the candidate and its measured numbers, retained — a negative result is still a result.

[B96] 17.5 · Technical and behavioural requirements

[B97] Governance layer — already ratified, reused verbatim from RMS-IQ-Core-2

[B98] A17.1  [CANON] Configuration lives outside code.

[B99] Optimizer and its parameters, learning-rate schedule, batch and epoch parameters, and adapter rank and target modules MUST live under training_params@v0, a sidecar configuration class with the same discipline as extraction_params@v0: versioned, ledgered, outside contracts/, no Parity contact. The effect is that a training configuration change is reviewable and auditable the same way a rule change is — not a deploy note buried in a pull request.

[B100] T-1.1, training_techniques_spec_v1.md

[B101] A17.2  [CANON] The seat ships empty.

[B102] No default recipe exists until the first training run fills it through the §3 optimizer-selection protocol (A17.5–A17.6). Nothing may pre-populate training_params@v0 by convention, template, or engineer judgement — the first value ever written to it must carry the measured comparison that produced it.

[B103] A17.3  [CANON] Lineage extends to configuration.

[B104] Every trained model's registry entry MUST cite the recipe_version that trained it. MOAC's lineage criterion (M-d) extends by this field, so “which configuration produced this model” is answered by reading the registry, never by asking whoever happened to run the job.

[B105] A17.4  [CANON] Revision is DEFAULT-class, but never unevidenced.

[B106] Recipe revisions carry no approval ceremony. Each revision MUST attach the measured comparison that justifies it and MUST write a ledger row. A revision without attached evidence is a defect — the absence of ceremony is a statement of trust in the evidentiary standard, not an exemption from it.

[B107] A17.5–A17.6  [CANON] The optimizer-selection protocol: two arms, identical conditions, parity mandatory.

[B108] The protocol executes at the first adapter training on real material, inside the P4-instrumented run. Its shape is one two-arm comparison — the current baseline optimizer versus a candidate, Muon named as the first — with identical training data, identical base model, identical evaluation sets, and an identical compute-budget cap, run on the smallest stratum that still yields a valid MOAC evaluation. Four measured outputs are reported for both arms without exception: target-stratum improvement (MOAC's M-a), non-target regression (M-b), wall-clock and GPU-hours to convergence, and calibration quality (an M-e input). Quality parity on M-a and M-b is mandatory for the candidate to remain eligible at all; compute-to-convergence is reported, never gating — a faster optimizer that regresses quality is not eligible regardless of its speed. The adopt/reject decision is then an Owner ruling made on the measured results, with no adoption threshold fixed in advance of the evidence, and verdict samples are uncurated per the platform's standing D-7 doctrine (evaluation inputs may be engineered; evaluation samples may not). On adoption, the winning arm writes training_params@v0 v1 with the comparison attached; on rejection, the candidate is recorded as tested, with its numbers, permanently. The identical protocol governs every future recipe-component candidate — this is not a one-time bootstrap, it is how the recipe seat is filled from now on.

[B109] A17.7  [CANON] Ensemble critics detect; they never decide.

[B110] Multiple reviewing instances are legitimate where a single critic's detection quality is insufficient, and prohibited from ever holding decision authority — the boundary follows from the platform's design (one walled learner, one reasoning faculty, the standing QA-1 rule that the layer detects and never decides) and is permanent, not a current-scope limitation. Deployment order is fixed: when seeded audits show a single critic's catch-rate below the standing bar on any fall class across two consecutive audits, rubric and context repair MUST execute first; an ensemble MAY deploy only if the repaired single critic still misses on a subsequent audit. Members MUST differ genuinely — a different base model or a materially different context shape — because same-base, same-context replicas are correlated reviewers that share failure modes and add cost without adding detection. All ensemble output is findings only; voting, override, and critic-of-critic structures are prohibited outright. Disagreement between critics is itself a finding class, routed to rulings like any other. Bounds: N ≤ 3 members without an explicit Owner ruling, with cost-per-review telemetry emitted per member, and the ensemble retires on its own kill metric — if its catch-rate gain over the single repaired critic falls under 10 percentage points after one full calibration cycle, it is rent not worth paying.

[B111] A17.8  [CANON] Cascade offload builds only against a measured shortfall, never speculatively.

[B112] A local-cascade — a local model drafts, an LLM handles only what the local model cannot — reduces metered spend where a cheaper model can filter most of a workload, but carries a documented failure mode: past a certain escalation rate, each escalated item pays twice, local and LLM both, and the cascade turns net-negative. The platform already minimizes LLM load by construction (the rung ladder, record-derived facts never re-asked of the LLM, the mechanical composition arm, the critic-succession seat), so a cascade is deliberately not pre-built. It MAY begin only when F3 telemetry, with cost columns active, shows LLM spend on a named seam exceeding a threshold the Owner sets at that time — no threshold exists in advance of metered evidence, and before the trigger fires, no cascade scaffolding, draft-model acquisition, or routing machinery may be built at all (the D7 fence). Its shape, once triggered, is local model drafts → deterministic acceptance check → LLM invoked only on rejects, where the acceptance check is rung-1 machinery, not a second model's judgement. It MUST emit its own kill metric — the double-pay rate, the share of items incurring both local and LLM cost — from its first run, and MUST retire if escalation makes it net-negative against the pre-cascade baseline.

[B113] A17.9  [CANON] Execution mode is explicit or the process refuses to start.

[B114] PERCEPTION_EXECUTION_MODE is read from the environment at import time and must be exactly “cpu” or “gpu”; an unset variable raises an import-time failure rather than defaulting silently, because a GPU deployment quietly running on CPU is the same silent-swap risk in the opposite direction from what governance normally worries about — it fails safe in the wrong direction, producing correct-looking but unrepresentative results rather than an obvious error. execution_mode is then carried in result telemetry, so attribution of GPU-hours and yield to a mode the record doesn't state is closed the same way fabricated model attribution is closed elsewhere in the canon.

[B189] DOCUMENT 18   Callable Skill Files

[B190] Callable Skill Files

[B191] A new promise — Promise #33. Owner-confirmed architecture (July 2026, RMS-IQ-Core-2); complete donor code exists but is not in the current build.

[B192] 18.1 · The promise, in plain language

[B193] A skill is a stay-running, key-scoped query capability over a defined corpus slice — an application calls it and receives governed answers, repeatedly, on the platform's own infrastructure. It is not model weights, and it is not a file handed over: governance does not end at delivery, because there is no delivery. It travels into every call, for the life of the skill.

[B194] 18.2 · The service that powers it

[B195] The existing inner-gate crossing infrastructure (Document 1), extended by the callable-skill donor package — complete implementation, ~356 LOC, present in both RMS-IQ-Core-2 and Akki-OS-V1: a frozen provisioning contract, a per-call governance gate, and write-once persistence. Not in the current build; sized by the builder at a clean ~40% LIFT into the W11 envelope alongside Document 17's runner.

[B196] 18.3 · Definition of the promise

[B197] The reasoning below is reused close to verbatim from the July 2026 architecture ruling, because the reasoning is the part worth keeping intact — a conclusion without it invites re-litigating the same ground later.

[B198] Why this needed its own ruling, not an extension of the export model

[B199] Every output the platform can produce looks, at first, like a variation on “produce something, then define who can access it.” Treating all outputs that way is a trap: it architects the live ones as static deliverables, and the mistake surfaces only once a skill gets queried a thousand times and turns out to need per-call governance the export model was never built to carry. The real distinction is not output-then-access. It is whether the system finishes and hands over, or stays running and answers.

[B200] Two classes, one dividing line

[B201] Hand-over: qualified data, a knowledge artifact, a trained model file. The system produces, packages, and delivers a finished thing; governance is enforced once, at export. Stay-running: a callable skill, an API feed. The system stays up and a consumer queries it repeatedly; governance has to travel into every one of those calls, live. Skills are stay-running by definition — an application queries them, they are not model weights, and the “trained behaviour” reading of “skill” belongs to the model-output form (§17), not here. This is not new architecture: it is the identical governance-travels-inline requirement the platform's integration surface already carries for API responses, now extended to a standing service rather than a single call.

[B202] What this fixes about the delivery model, concretely

[B203] Hand-over outputs continue to fit the existing two-perimeter export model without change. Stay-running outputs need per-call inline governance, which is the reason this document exists as its own promise rather than a line item under an existing one — the liability model, the access architecture, and the governance surface for “a file the consumer runs themselves” and “a service they call on the platform's own infrastructure, forever” are genuinely different products, and conflating them is what produces the failure mode described above.

[B204] Grain is per_claim and synthesized_whole, per query — deliberately distinct from a knowledge artifact's per_claim/aggregated grain, because a skill composes a fresh answer to each specific question rather than exporting one fixed graph once.

[B205] 18.4 · Delivery experience expectations

[B206] What the organisation experiences (human-facing)

[B207] Provisions a skill over a frozen, named corpus slice and hands a consumer a scoped key and an endpoint — nothing else about the underlying data.

[B208] Revokes a skill and has every subsequent call refuse immediately — enforcement is server-side, not a client convention that can be ignored.

[B209] Reads the provisioning record for any skill: who was granted what scope, over which slice, from when to when.

[B210] What a consuming system experiences (machine-facing)

[B211] Calls the skill repeatedly and receives an answer with its class carried inline on every response — never a response the inner gate hasn't governed.

[B212] Queries below the skill's floor and receives the refusal envelope, not a degraded or partial answer.

[B213] Cannot reach a slice wider than the one bound at provisioning — a changed slice is a new skill, never a silent edit of the old one.

[B214] What is produced and retained

[B215] The provisioning record itself: skill_id, corpus_slice_ref, key_grant_id, floor, scope, endpoint_path, provisioned_at, and revoked_at once set.

[B216] Every call's governance class, carried on the response, per the inner gate's existing per-call record discipline.

[B217] 18.5 · Technical and behavioural requirements

[B218] A18.1  [CANON] The provisioning record, reused verbatim.

[B219] This is the frozen contract every skill is created against — not a draft to redesign, a specification already anchored to owner rulings TF-E2/TF-E4 and reused as-is:

[B220] Callable-skill provisioning record

[B221] { skill_id, corpus_slice_ref: artifact-store key,

[B222] key_grant_id, floor, scope, endpoint_path,

[B223] provisioned_at, revoked_at?: str }

[B224] §3.7 annex, RMS Intelligence spec, 2026-07

[B225] A18.2  [CANON] The slice freezes; it never edits.

[B226] Corpus slice binds at freeze, an endpoint is provisioned against it, and a key is scoped to that endpoint. The slice persists via the artifact store, write-once. If the underlying material needs to change, the platform provisions a new skill against a new slice — it does not mutate the old one, because a mutating slice would mean the governance decision made at provisioning (“this key may see this material”) silently stops describing what the key can actually reach.

[B227] A18.3  [CANON] Governance rides every response, not just the first one.

[B228] Every response carries its class inline through the inner gate's per-call governance — the platform's existing live-response contract, applied here to a standing service instead of a single crossing. Nothing about the mechanism is new; what changes is that it now runs once per query for the life of the skill, rather than once per delivery.

[B229] A18.4  [CANON] Below the floor is a refusal, never a degraded answer.

[B230] The standard is enforced per call. A query that falls below the skill's floor returns the refusal envelope — the same governed refusal shape used everywhere else on the platform — rather than a thinner or hedged version of an answer.

[B231] A18.5  [CANON] Scope is enforced server-side, not by client discipline.

[B232] Access rides the engineer key-grant records. A consuming application's own good behaviour is never the control — scope is checked at the gate on every call, so a compromised or careless client can narrow what it asks for but cannot widen what it's able to get.

[B233] A18.6  [PROPOSED] Async delivery, if fresh extraction ever backs a skill's answer.

[B234] Not yet confirmed as part of skill files specifically, but already a ratified contract shape elsewhere in the same source, and the natural fit if a skill's query ever requires extraction rather than a warm read: fork at admission — warm returns a synchronous full response; fresh returns 202 with { objective_id, status: accepted, delivery_estimate, quote? }. States move accepted → running → delivered | refused, with a late refusal a normal terminal state carrying the same refusal envelope, never rendered as a failure. Delivery is a thin webhook plus a governed fetch: the webhook payload is { event, objective_id, trace_id, status } — never claim content — and the actual result is pulled over the caller's authenticated key, scope enforced there, not pushed to an app-configured URL, because pushing claims to arbitrary endpoints would be an egress path the gates don't control. No partial egress, including on cancellation — a cancelled run is still ledgered. An idempotency key is required on submission so a retried call cannot double-commission or double-charge.

[B235] §7, RMS Intelligence spec, 2026-07 — proposed here for skill files by extension, not yet owner-confirmed for this specific case

[B236] A18.7  [RULED] The concept is owner-confirmed; its adoption into this canon is not inherited.

[B237] “Skill files” as a named artifact appear nowhere in the 16-document canon. The architecture above is owner-confirmed [STAKED] in the July specification — that ruling is real and reused here verbatim — but formally landing it as Promise #33, with its own number in this codebase's canon, is this document's own act. It should be read as adoption, not as a restatement of a decision already made at this level.

[B238] A18.8  [OPEN] Complete donor code exists; it is not in this build.

[B239] Roughly 356 lines across RMS-IQ-Core-2 and Akki-OS-V1 implement the frozen provisioning contract, the per-call governance gate, and write-once persistence — a clean ~40% of it liftable directly. Build scope: the remaining contracts, the corpus-slice custody seam (shared with Document 17's execution layer), and a skill-files registry surface on the frontend, delivered inside the same W11 envelope as the trainer runner.

[B240] 18.6 · What must be true for the service to deliver as intended

[B241] A corpus slice is bound and frozen before an endpoint is ever provisioned — no skill is provisioned against a moving target.

[B242] No response leaves the inner gate without its governance class carried inline.

[B243] Revocation is enforced at the gate, not at the client — a revoked key produces a refusal even if a consumer never checks its own state.

[B244] A widened or changed slice is never expressed as an edit to a live skill — only as a new one, with its own provisioning record.

[B246] DOCUMENT 19   Quality Assurance & Evidence Integrity

[B247] Quality Assurance & Evidence Integrity

[B248] Two parts. Part A, the Critic Seam, is CANON — Owner-ratified 2026-07-15, reused here in full. Part B, the Evidence Protocol, is PROPOSED — my own prior synthesis from an August chat, explicitly offered there for ratification and never confirmed adopted; checked directly against both repositories, with no trace of a build or a ruling. It is written here to the same standard as everything ratified, with its status stated plainly rather than smoothed over.

[B249] 19A.1 · The promise, in plain language

[B250] Every intelligent worker in this build — the builder agent executing phases, any LLM worker the platform harnesses at runtime, and the ruling authority's own drafts and rulings — has its output checked against the on-disk record before it can mislead, not corrected by hand after it already has. The layer mechanizes exactly the half of quality assurance that is mechanizable: verification against canon. It deliberately does not attempt the other half — reframing the problem, changing the product's direction — which remains the Owner's seat, permanently.

[B251] 19A.2 · The service that powers it

[B252] No single named engine; a layer integrated into the standing build loop itself — the Registry (every function's mandate, promise, service trace, enforcement, cost, owner), the Registry Doctrine's binding rules, and the existing ruling loop (dispatch → Stage A proposal → escalation → ruling → execution → close report). It extends two precedents already standing in the build rather than introducing new machinery: the standing queries' findings-not-actions pattern, and Targeta's wall — the constitutional precedent that a subordinate intelligence detects and optimizes but never decides, which the critic inherits verbatim.

[B253] 19A.3 · Definition of the promise

[B254] Origin: every check mechanizes a catch the Owner actually made, by hand

[B255] This is not a speculative layer designed against a hypothetical failure mode. Five documented fall classes from this build's own correction history fix its boundary: memory-ruling (asserting something false against the on-disk record — the origin of doctrine rule D-11); re-derivation (proposing something as fresh advice that the Owner's own specification already states, caught once at the cost of a full audit cycle); invented scope or schedule (work categories or sequencing authored without instruction, against an explicit fence); false status (a register claiming a close was never returned while it sat on disk, a day old); and unclassed assertion (values and claims stated without their evidence class). The line that fixes the layer's boundary: every catch above is a verification — the truth existed on disk and the worker diverged from it. The Owner's other interventions in this build's history were frame changes — rewriting canon rather than diverging from it — and no layer that verifies against canon can catch a correction to canon. Frame authority is permanently outside this layer's reach.

[B256] Five design principles, each tied to a standing precedent

[B257] Detect, never decide — the layer emits findings; every consequence is a ruling. A QA layer with veto power would be a governor nobody mandated.

[B258] Canon is the oracle — all deterministic verification resolves against the on-disk record, never a summary, a context window, or another model's recollection.

[B259] Zero loop drag — the layer adds no turns to the dispatch loop; deterministic checks run as cells at submission boundaries, the critic runs asynchronously between turns, findings arrive with the artifacts they review, never before them.

[B260] Halving, not zeroing, stated honestly — a critic sharing a worker's blind spot misses what both cannot see; the claim is a measurable shrinkage of the residual, not its elimination, which is why the layer measures itself rather than trusting itself.

[B261] The layer pays rent — its own catch and false-alarm ledger is standing; if it stops catching and starts noising, it shrinks or retires by ruling, the same discipline every other function on the platform is held to.

[B262] 19A.4 · Delivery experience expectations

[B263] What the organisation experiences (human-facing)

[B264] The Owner's reviewing role compresses; it does not disappear. Instead of reading every artifact, a measured fraction of critic findings and all-clears is sampled for review — the sampling rate itself shrinks as the critic's measured reliability accumulates.

[B265] Sees findings, never a blocked workflow — the one exception is a hard format gate on missing required sections, form only, never substance.

[B266] Reads a standing calibration ledger: the critic's catch-rate and false-alarm rate per worker class, versioned like model calibration, so “how much can I trust this layer” is a citable number rather than a felt impression.

[B267] What a consuming system experiences (machine-facing)

[B268] A Stage A proposal or close report submitted without its required sections — including the self-audit table — is rejected at the format gate before it enters the loop at all.

[B269] Every other check returns a finding row, never a block: citation mismatches, untraceable scope, unclassed assertions, schema gaps, status contradicted by the repository, and lexical collisions with existing Registry entries all surface as findings, not failures.

[B270] What is produced and retained

[B271] Findings reports, evidence-classed and cited like every other producer's output on this platform — an unclassed finding is itself a finding.

[B272] The calibration ledger, carrying a staleness field; a critic whose calibration falls outside its window renders its findings UNCALIBRATED rather than silently stale.

[B273] The checks themselves register in the Registry with their own rows — they are functions, and functions pay rent like every other function on the platform.

[B274] 19A.5 · Technical and behavioural requirements

[B275] Tier 1 — deterministic record-verification (rung 1)

[B276] Six check families, all mechanical, all resolving against the repository, running on Stage A proposals and close reports at submission:

[B277R1] Check | Definition | Mechanizes

[B277R2] RV-1 citation-existence | Every SHA, file path, ruling id, registry row id, and contract name cited resolves to an existing on-disk object; cited SHAs match the object's actual hash. | Memory-ruling

[B277R3] RV-2 scope-trace | Every work item traces to an authorizing instrument — a dispatch, a register row, a ruling. Untraceable items are scope-invention candidates. | Invented scope

[B277R4] RV-3 evidence-class presence | Classed assertions (status, values, verdicts) carry FACT/NORM/DEFAULT or fact/recalled/inferred, matching their class's required form. | Unclassed assertion

[B277R5] RV-4 schema-completeness | Required sections present — band, escalations, registry rows, self-audit table for proposals; gate roster, artifact SHAs, self-audit table for closes. The one hard gate (QA-2). | Submission discipline

[B277R6] RV-5 status-truth | Every status claim about an on-disk artifact is cross-checked against actual repository state at submission time. | False status (the LT-1 class)

[B277R7] RV-6 novelty collision | Proposed function ids, promise ids, and concept labels are matched against the Registry and mandate documents; collisions flag for semantic confirmation. | Re-derivation, first line of defense

[B278] Tier 1's conceded limit, stated by the source rather than discovered later: it verifies form and existence, not pertinence — an artifact can cite real SHAs for irrelevant objects and pass. Pertinence is exactly what Tier 2 is for; the two tiers are designed as a pair, and adopting Tier 1 alone buys the cheap half while advertising the whole.

[B279] Tier 2 — the critic pass (rung 3/4), independent by construction

[B280] An independent model instance reviews each Stage A and close asynchronously, after landing, against a fixed six-item rubric drawn directly from the Owner's own catch history: anti-re-derivation (does this already exist in the record under any name), anti-fabrication (is any claim stronger than its evidence class permits), the conflation test (does every proposed function trace to a real named service), scope semantics (does the work's substance stay inside the dispatch's intent, beyond what the mechanical trace alone catches), enforcement honesty (is any rule proposed whose only enforcement is prose), and self-audit audit (does the artifact's own self-audit table's reasoning hold, or is it reflexive pass-stamping). The critic never shares the worker's conversation — its context is exactly the artifact under review, the canon set, and the rubric, never the worker's reasoning or drafts, because a critic reading the worker's own justification inherits the worker's frame, which is precisely the blind-spot-sharing failure the design exists to avoid. No worker ever critics its own output; where critic and worker share a base model, independence is by context isolation alone, and Tier 3's seeded audits exist specifically to measure whether that isolation is sufficient rather than assume it. The critic runs at the cheapest sufficient rung, and its findings carry the same evidence-classing and citation discipline as every other producer on the platform.

[B281] Tier 3 — human calibration sampling: the Owner's role compresses, it does not vanish

[B282] Verdict sampling: a fraction of critic findings and all-clears (default 20% of findings, 10% of all-clears, decaying as measured reliability accumulates) is human-scored as a true catch, a false alarm, or a miss.

[B283] Seeded-defect audits: on a standing cadence, a known defect from a documented fall class is deliberately planted in a review copy — never a landing artifact — and the critic's catch or miss is recorded. This is the only honest measurement of a reviewer that mostly reports clean: detection proven on known positives, drawn across fall classes, never curated toward the critic's own strengths.

[B284] The calibration ledger: catch-rate and false-alarm rate per worker class and rubric item, versioned like model calibration, with a staleness field — a critic whose calibration is stale past its window renders its findings UNCALIBRATED at the point of use, the same honesty rule the platform applies to model confidence generally.

[B285] Behavioural rules, binding on adoption

[B286] QA-1  [CANON] Detect, never decide. No finding blocks execution, edits an artifact, or gates a phase — every consequence is a ruling. One scoped exception: QA-2.

[B287] QA-2  [CANON] The format gate. Schema-completeness (RV-4) is the single hard gate — a submission missing its required sections is returned for completion before it enters the loop. Form, never substance.

[B288] QA-3  [CANON] No self-review. No worker critics its own output; independence is by context isolation, itself measured by seeded audits.

[B289] QA-4  [CANON] Findings carry the honesty grammar — every finding is evidence-classed and cited; an unclassed finding is itself a finding.

[B290] QA-5  [CANON] The layer pays rent. The catch/false-alarm ledger is standing; a layer that stops catching shrinks by ruling. A second QA layer above this one is a meta-spiral defect on sight.

[B291] QA-6  [CANON] Frame authority is untouchable. No check, rubric item, or finding may dispute an Owner ruling, a service sentence, or a frame decision — the layer verifies divergence from canon; it has no standing on changes to canon.

[B292] 19A.6 · What must be true for the service to deliver as intended

[B293] It is not a governor — it holds no mandate, asserts nothing about the estate, and gates nothing but submission format.

[B294] It is not the Owner's replacement — the build's largest course-corrections were frame changes, which this layer would catch none of, by design; claiming otherwise is exactly the overclaim its own anti-fabrication rubric item exists to flag.

[B295] It is not inline — nothing here adds a synchronous step to any serving path or a turn to the dispatch loop.

[B296] It makes no zero-residual claim — it halves the residual, measurably and repeatedly, and its own dashboard is built to show its misses, not hide them.

[B332] DOCUMENT 20   The Model Capability Register

[B333] The Model Capability Register

[B334] Closes Promise #24 (Document 14), which Document 17 (A17.10–A17.11) named but only partly landed. Extends the existing models_registry.v0.json mechanism — the same registry, not a new one — with real candidate population and a formal resolution rule. Owner-ruled: the PROPOSED rows below (A20.3–A20.10) are adopted now as live PROPOSED-class config, not held for individual per-model ratification — license verification is already complete for each, and A20.13's calibration-decides mechanism is itself the ratification step.

[B335] 20.1 · The promise, in plain language

[B336] Every training or extraction objective is served by the strongest license-verified base model for its actual task — never a default reached for out of habit, and never a model the business user has to know exists, name, or choose. This is Promise #24's own language: “the platform holds a curated set of the strongest openly-available pretrained models, organised by task each is good at, so that … the platform trains its own model for a task starting from the best available baseline.”

[B337] 20.2 · The service that powers it

[B338] The existing model registry (backend/services/perception/models_registry.v0.json, Owner-ruled 2026-07-10 and extended 2026-07-15) — today four C1 candidate classes (text, document, vision, audio), two with named comparison-arm members (Qwen3/3.5, Llama) and two registered empty (document, vision), plus audio's own CI-fixture-only entry. This document populates the two empty classes with license-verified real candidates and formalises how the Objective Wizard resolves a stated task to a dimension and a candidate — the registry's structure does not change; what it holds, and how it gets read, does.

[B339] 20.3 · Definition of the promise

[B340] Listing and availing, not ranking and asserting

[B341] The register's job is to make license-verified candidates available per dimension — it does not itself declare a single global “best” model, because best is a function of the task, the population, and the constraints stated in a specific TargetOutcome, not a property a model carries on its own. A candidate strong on one axis (vocal realism, document layout, long-context reasoning) is not automatically the right pick for a different task in the same dimension. This is why the register supplies eligible candidates and calibration (§17.3, mandatory first stage of every training plan) proves fit on real data — the register narrows, calibration decides.

[B342] Four dimensions, license-verification only at registration

[B343] Per the existing C1-candidate discipline: registering a class or a candidate is license verification and parameter disclosure only — zero download, zero compute. A specific member's weights are pulled and checksummed only at acquisition, when a real objective actually needs it. This document adds real, current candidates to the document and vision classes, which existed only as empty placeholders before it.

[B344] Resolution is compiled, not chosen

[B345] A business user states an objective in plain language. The Objective Wizard's existing compile step (§17.4d) resolves the stated task to a dimension the same deterministic way it resolves population to register strata — the model pick is a third compiled artifact alongside TargetOutcome and Collection Schema, never a menu rendered for the user to browse. This extends, rather than duplicates, the wizard's existing discipline that no business user hand-writes a technical parameter directly.

[B346] 20.4 · Delivery experience expectations

[B347] What the organisation experiences (human-facing)

[B348] States the objective in plain language and never sees a model name during that conversation — the same discipline the wizard already applies to every other technical parameter.

[B349] Sees the resolved candidate only as part of the commission's record afterward, with the reasoning — which candidates were eligible, which was picked, and why — available on request, never pushed into the front-of-conversation flow.

[B350] Where a dimension has more than one strong eligible candidate, sees calibration's measured comparison between them before a full run commits — the same Sampling & Reflection stage already mandatory for every training plan, now also settling model choice, not only recipe choice.

[B351] What a consuming system experiences (machine-facing)

[B352] TargetOutcome's task and domain fields resolve deterministically to a dimension; an objective that doesn't resolve cleanly is flagged for the same census-style clarification an unresolved population already triggers.

[B353] The resolved candidate's license, checksum, and origin data flow automatically into training_params@v0 and the training manifest — no separate step re-enters this information by hand.

[B354] What is produced and retained

[B355] The resolution record itself: which candidates were eligible for the dimension, which was selected, and the calibration evidence (where more than one candidate was tested) the selection rests on — permanent, part of the same provenance chain the training manifest already carries.
