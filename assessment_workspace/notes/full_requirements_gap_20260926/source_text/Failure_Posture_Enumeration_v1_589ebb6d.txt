[B5] 1   The Platform Default

[B6] FP-1  Every component in the Trusted Computing Base fails closed by default. An evaluation that cannot complete — configuration unset, a dependency unreachable, a check erroring — refuses the operation it governs. This is the default; §3 lists the components that correctly depart from it, and why.

[B7] FP-2  A gate whose governing configuration is unset or fails integrity verification at load refuses by default rather than passing by default. This absorbs security_architecture_v1's SEC-4 (MOAC), SEC-6 (the distance gate), and SEC-7 (the admission probe) as one rule rather than three restatements of it — an unconfigured gate is a closed gate, platform-wide, not per-component.

[B9R2] SyniSense — chokepoint | Custody policy unreadable; de-identification step errors; re-identification key unavailable | Fail-closed | The crossing attempt itself — who, what, when — written before the attempt, so a failed crossing is still evidenced

[B9R3] SyniSense — closed network | Allowlist configuration unreachable | Fail-closed | No outbound connection attempted; the refusal reason

[B9R4] Solva — assertion-boundary seam | Anchor map cannot be computed; source material unreachable | Fail-closed | The unanchored draft is discarded, not served; the refusal with structured reason (A5.5)

[B9R5] Northena — objective-freeze | Freeze record unreadable at a hand-off point | Fail-closed | The job halts rather than proceeding on an unverifiable scope

[B9R6] Mtafiti — registry | Write path unavailable | Fail-closed for writes; fail-safe-open for reads of already-committed data | Last successfully committed state remains queryable even while writes are refused

[B9R7] Targeta — yield wall / MOAC | Criteria configuration unset or unverifiable | Fail-closed | The run's own artefacts remain intact; nothing is marked accepted

[B10] 3   The Departures — Where Fail-Safe-Open Is Correct

[B11] Two departures from §1's default, both already correct in the system as built, now stated as deliberate rather than left to be discovered.

[B12] FP-3  Mtafiti's read path fails safe-open: a write failure never blocks a query against already-committed estate composition. The alternative — refusing to answer “what exists” because “what changed most recently” cannot be confirmed — would make an outage indistinguishable from data loss to everyone reading the registry, which is a worse failure than serving slightly stale data marked as such.

[B13] FP-4  The Watch's already-active containments persist through a Watch outage rather than lapsing. This is fail-closed for new decisions and explicitly not fail-open for standing ones — the two are evaluated separately, and conflating them would silently release every contained actor the moment the Watch itself failed, which is precisely when containment matters most.

[B14] Recovery time objective and recovery point objective for the Ledger writer specifically are covered in the Business Continuity Annex (document 8 of this set), not restated here — this document specifies posture per component; that one specifies how long a failure may last and how much may be lost before it is a breach in its own right.

[B15] 4   Standing

[B16] A component added to the Trusted Computing Base under tcb_enumeration_v1's own standing clause is added here in the same turn — posture, failure types, and preserved state, not deferred to a later pass. §1's default applies until stated otherwise; a new TCB member that departs from it states so explicitly, the way §3 does for Mtafiti and the Watch.
