1   The Test, Applied Literally
BA-1.1 sets a conjunction, not a list of examples: deterministic, and protection-critical. A component can be highly consequential and still fail the test if it is learned — CIF is the standing example, excluded under BR-9.1 regardless of how central its ideation is. A component can be perfectly deterministic and still fail the test if nothing depends on it — deterministic housekeeping code that no guarantee cites is not TCB by virtue of being predictable.
“Deterministic” is evaluated at the level of the mechanism actually making a decision, not the subsystem that hosts it. Several entries below split a subsystem in two for exactly this reason: the decision point inside it is deterministic even where the subsystem's broader function is not.
“Protection-critical” is evaluated by BA-1.1's own clause: would this component's failure falsify a stated guarantee. Each row below names the guarantee.

3   Minimisation — What Was Kept Out, and Why That's Correct
TA-1.2 requires the TCB stay small by design, excluding a learned or non-critical component “even where it is operationally central.” Four exclusions above are worth stating plainly rather than leaving as table rows, because each is operationally central and excluded anyway: Solva's actual reasoning — the platform's most visible capability — is not TCB; CIF, the self-improving core of the training story, is not TCB; Grey Mirror, the detection half of the platform's own security layer, is not TCB; and the Deck Rendering Engine, despite being genuinely, verifiably deterministic, is excluded because determinism alone was never the bar.
This is the minimisation property working as intended, not a set of gaps. A small TCB is a stronger guarantee than a large one — it is what makes G-2's forthcoming architecture description and G-6's security architecture description tractable to write and to verify.
