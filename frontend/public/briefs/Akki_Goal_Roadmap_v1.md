## 1. How execution will work

### One milestone is a working promise, not a component inventory

Each milestone contains three kinds of sprint work: **recover and connect what exists; complete the missing behaviour; run and repair the whole journey**. A missing input, descriptor, module, measurement method, approval reference, dataset or test is a task inside that milestone—not an automatic new request to the owner and not a separate governance programme.

Before each milestone, I will read all repository implementations relevant to its outcome, their dependencies and existing evidence, identify reuse in the current build and supplied repositories, and make a short readiness list: **available / recover / wire / repair / build / measure / externally blocked**. Earlier audits are leads, not proof of today's defects. No full-programme audit must finish before useful delivery starts.

### Complete reuse review inside EVERY milestone's readiness phase

This is part of the first work package of M1–M10, not an eleventh milestone or another owner approval gate.

1. **Inventory everything built for the outcome.** Start with the current workspace and the pinned Root inventory; include backend services, frontend bindings and owner templates, workers, contracts/schemas, storage/writers, configuration, scripts, tests and prior decisions. Follow imports, callers, route assembly and shared dependencies. Locate alternatives in the supplied Core/OS and relevant linked repositories before calling a capability missing.
2. **Read the actual implementations in full.** A filename match, symbol index, README, representative path or passing mock is insufficient. Read active and alternative implementations, fallback/refusal/recovery branches and tests; trace generated UI to its authoring source. Record inaccessible, unread, obsolete and unrelated material separately. Never call unread code absent or claim every repository file was read when only selected paths were inspected.
3. **Trace outcome to effect.** Identify the ordinary user entry, governing authority, selected provider/worker, real effect, existing writer, receipt and every required consumer. Distinguish code present, wired, runtime available and live-proven. Record whether estate reads occur outside E1.
4. **Choose the smallest justified change.** Reuse working code; connect an unwired implementation; repair a demonstrated defect; extend a real partial implementation. Propose new code only for a specific requirement not satisfied by any inspected candidate. No parallel Registry, queue, memory plane, execution lifecycle or UI replacement.
5. **Attach the review to the existing milestone work record.** For each requirement: repository/pin + file/symbol + read status → active caller and dependencies → existing evidence/limits → reuse/wire/repair/build task → existing acceptance test ID. Carry shared reviews forward and inspect their changes; do not repeatedly rebuild or reread unchanged code without purpose.

Across the milestones, this accounts for the built product progressively. An unmapped implemented capability must receive an owning milestone or an explicit out-of-scope reason; it cannot disappear from the inventory. Readiness closes with the reusable implementation and exact delta identified, not with an unsupported assurance that everything works.

### Gates and sequencing

Main delivery order: **M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 → M9 → M10**.

- A milestone's gate opens the next milestone's integrated acceptance and delivery claim. All mandatory acceptance runs must pass. A failed or blocked run remains open; a mock, skip or documented gap is not a pass.
- Independent preparation and work packages may run in parallel. This is not permission to bypass a gate. For example, GPU corpus/runner preparation starts after M1, and infrastructure qualification can proceed when credentials arrive; M9 completion still requires its upstream product gates.
- A shared prerequisite is completed in the first milestone that needs it. Tenant scope, source authority, basic usage accounting and existing Watch protection are not postponed because broader verification occurs later.
- Every new operation added after M2 reruns the relevant Watch coverage tests; M2 is not a perpetual certificate for paths that did not exist when tested.
- Dependencies genuinely outside our authority hold only affected tasks. Independent work continues. We do not claim whole-platform completion while a required branch is held.
- Use three truthful gate results: **PASS, FAIL, BLOCKED**. Conditional scope belongs in the pre-run manifest, not a “conditional pass.” Dormant classes retain the specification's no-claim posture; observed required classes cannot be declared dormant to get a green gate.

### Definition of a sprint

A sprint is one of the numbered work packages below, ending in demonstrable behaviour and tests. It is not an invented number of days or a quota of code/tests. The milestone ends only after its integrated acceptance pack passes. Fixes stay with the sprint that failed; do not move them into a vague later hardening phase.

### Test contract, fixed before the run

Use the existing objective/commission, test and result records. Do not build another workflow engine for this roadmap. Each acceptance run records:

`run ID · promise/source anchor · tenant/role · scope and population/snapshot · prerequisites · actual model/runtime/version where relevant · expected output/effect · metric and denominator · threshold authority · pass/fail script · output/evidence references · result · next repair task`.

Acceptance criteria are set before observation, not after seeing the result. Where a number is absent, recovering the ruled value or running the specified calibration is part of the milestone. A calibration run is not its own independent acceptance run. The owner is asked only where a decision genuinely belongs to them.

Every milestone tests: **useful success; relevant refusal/failure; interrupted/repeated action; current rights and tenant separation; persistence and visible outcome**. Purely observational reads use read failure/re-entry rather than an irrelevant cancellation feature. Tests must exercise the active product path, not only helpers.

Real estate/model/delivery outcomes require real admitted services. Controlled test inputs for faults, abuse and mirage are deliberately labelled **SYNTHETIC TEST DATA**, but detection/enforcement/recovery must run through the real services. **MOCKED providers cannot establish live success.** Destructive, hostile or permission-mutation probes run in isolated authorised test scope, not against live tenant production data.

### No control without a purpose

For each timer, gate or additional check, answer: **which promise does it protect, where is that anchored, what failure does it prevent, and is there already a mechanism?**

- Keep anchored protection that enables reliable function; integrate it into the journey.
- Remove builder-invented restrictions or duplicate machinery with no authority or demonstrated functional purpose. First trace callers and prove the protected behaviour still works; retain the change history.
- Do not delete a ratified control just because its original rationale was not in the last handoff. Recover the anchor first; bring only an actual conflict back to the owner.
- **Census freshness:** structural/source change drives scoped rediscovery. Do not add a weekly census timer merely to make a status green (Canon 4 §8; Doc 9 B5.6).
- **Watch containment expiry:** retain it because it limits harm to an innocent actor. Do not apply that expiry to confirmed severance where Canon 8 §7 explicitly requires a hold. Reuse the existing action mechanism.
- **Operational timeouts:** retain bounded connection/job/resource handling where it prevents a stuck operation; distinguish those timeouts from invented policy barriers. No arbitrary sleeps, forced waiting or retry loops to simulate progress.
- Preserve owner-provided UI and product vocabulary. Evidence supports the experience; users do not manage our implementation machinery.
