## §A · Terminology (R-18 Part 1 · E2)

**Canon anchors:** R-18 Part 1.

In build artefacts (grounding briefs, PR titles, commit messages, seal notes, the SER's own sections), the word **"Canon"** means **(a) only** in R-18's authority ladder — i.e. the ratified canon rules carrying IDs: Documents 0–20 and amendments through `watch_learning_v1`.

The **System Engineering Reference (SER)** is cited as **`SER §x`** (or `SER Part B §…`, `SER Part C §…`, `SER Part D §…`). It is **never** cited as "Canon". The SER is the engineering derivation of canon, not a replacement for it.

**Direction of authority (R-18 Part 1):** canon > SO > SER > contract schemas > code. A lower layer NEVER amends a higher one; every conflict resolves upward. Where SER and canon conflict, canon prevails and the SER is corrected — never the rule.

**Canon anchors:** R-18 Part 1.

## §C · D.6 rewrite (R-18 Part 1 · E4 · E5)

**Canon anchors:** R-18 Part 1.

### §C.1 · `canon_ref` field added to `requirements.yaml` rows (E4)

The generated `requirements.yaml` (D.6's output) gains a **`canon_ref`** column per row. Value:

- an **existing registry ID** from the canon corpus (e.g. `A5.19`, `DAP-14`), OR
- the literal string **`none-new-needs-ratification`** for a genuinely new requirement not derivable from an existing registry entry (which then triggers a ratification desk-item).

**Documentation-check failure condition.** A requirement row with **neither** a `canon_ref` **nor** a `test_id` fails the documentation check. This mirrors the existing rule that a row without a `test_id` already fails; R-18 tightens it so a row lacking BOTH also fails.

Concrete D.6 codegen bump:

```yaml
- id: <req_id>
  text: "<verbatim requirement>"
  canon_ref: <registry_id | none-new-needs-ratification>
  test_id: <test path::name | none-new-needs-test>
  # If canon_ref is `none-new-needs-ratification` AND test_id is `none-new-needs-test`
  # the documentation check fires RED.
```

**Runtime check landing.** The D.6 documentation check that fires RED on `canon_ref == null AND test_id == null` is the "canon_ref check active" deliverable in R-18 Part 8. Errata lands the rule here; the code-side test lands under a downstream CP once M11/M12 gate-release conditions are green.

### §C.2 · D.6 "supersedes" line struck (E5)

D.6 previously carried a line to the effect of "this document supersedes that count". **STRUCK.** The SER **extends and cross-references** the master requirements register; it does not supersede it. The register remains the authority for requirement enumeration; the SER derives from and points into it.

**Forward text (replacing the struck line):**

> This SER derives requirements from the Master Requirements Registry. It extends the register with engineering context (test IDs, canon anchors, absorption cycle) and cross-references it — it does not supersede the register's count or authoritative status. Where SER and register conflict, the register (as an artefact of ratified canon) prevails.

## §D · C.3.3 and C.3.5 rewrite (R-18 Part 3 · E8)

**Canon anchors:** A5.3, A5.19, A5.2. (See E8 in DECISIONS R-18 entry.)

### §D.1 · SER §C.3.3 · I-2 rewrite

**Before (implicit prior reading):** the action taken on a Watch verdict was derived by policy from `(category, certainty)` — with `certainty:0–100` and `min_certainty` as gating inputs.

**After (R-18 Part 3 verbatim binding):**

> The action taken is exactly the registry entry for `(category, certificate satisfied)`.

- **`category`** — one of the canon-registered Watch action-class categories (per A5.3, which excludes `destroy` by name).
- **`certificate satisfied`** — a boolean derived from whether the verdict's certificate `{requirement_id, data_points[], observation_refs[]}` (per A5.19) is populated and each of its fields validates against the paired schema (per T-c Option (ii) extended, R-18 Part 2 · E6). A verdict with an incomplete certificate has `certificate satisfied = false` and MUST NOT trigger the registered action; the runtime path stays in the refuse-and-log lane.

**No confidence field appears anywhere in the I-2 path.** `certainty`, `confidence`, `score`, `strength`, and `probability` are forbidden by the T-c schema (per E6 signature-as-guard test). Their absence is enforced structurally, not by convention.

### §D.2 · SER §C.3.5 · I-2 mirror

Same rewrite as §D.1 applies to §C.3.5's I-2. The action lookup is a deterministic map from `(category, certificate satisfied)` to the registry entry; there is no probabilistic branch.

## §E · C.11.5 and C.11.6 rewrite (R-18 Part 3 · E9)

**Canon anchors:** AC-13, A5.3.

### §E.1 · Sever definition (verbatim binding)

**Before (implicit prior reading):** sever might have been read as "delete the runtime" or "terminate the agent process".

**After (R-18 Part 3 verbatim binding):**

> **Sever** freezes the agent session and revokes its credentials (AC-13); it **does NOT delete the runtime**.

**Operational implications:**

- The session enters a frozen state — no new tool calls, no new state transitions, no new ledger writes.
- All active credentials issued to the session (tokens, session keys, tenant-scoped principals) are revoked at the credential authority per AC-13. Downstream services reject any residual call from the frozen session.
- The runtime process itself continues to exist for post-hoc inspection, evidence preservation, and independent-role verification (per §F below · I-4).
- The runtime is disposed of only through a separate, canon-registered decommissioning path (not via sever).

### §E.2 · Contain vs sever relationship

**Contain** (per A5.3) restricts the agent's action surface to a read-only or bounded set without freezing the session. **Sever** freezes it entirely and revokes credentials. Both actions are Watch response verbs; both are ledgered per B.4 (see D-19 · R-18 Part 4 · E15 for the ledger-unavailable amendment).

## §F · I-4 rewrite (R-18 Part 3 · E10)

**Canon anchors:** AC-2(b).

**Before (implicit prior reading):** the runtime autonomously advanced through ladder rungs on its own checks.

**After (R-18 Part 3 verbatim binding):**

> The runtime checks ladder conditions and **proposes** advancement; a named role independent of the deploying operator ratifies it (AC-2(b)). **No rung advances on the runtime's check alone.**

**Operational implications:**

- The runtime computes whether ladder pre-conditions for the next rung are met and emits a **proposal** to advance. The proposal is a ledger row of kind `ladder_advancement_proposal` bearing the runtime's evidence.
- Advancement is gated on a countersign from a **named independent role** — independent of the deploying operator, per AC-2(b). The countersign is a ledger row of kind `ladder_advancement_ratification` bearing the ratifier's principal.
- Without the countersign, the runtime remains at the current rung. Countersign expiry follows the Part 5 default: **7 days after countdown end**.
- The two-signature pattern (runtime proposal + independent ratification) mirrors the Watch two-signature ceremony for high-authority actions.

## §G · A.4 rewrite (R-18 Part 3 · E11)

**Canon anchors:** BA-1.1, `tcb_enumeration_v1`.

### §G.1 · TCB membership test

**Before (implicit prior reading):** TCB membership might have been read as a policy declaration or a curated list.

**After (R-18 Part 3 verbatim binding):**

> The TCB membership test is **BA-1.1 verbatim** — deterministic, and its failure would falsify a stated guarantee.

**Operational implications:**

- Membership is not decided by opinion, taste, or curator preference. It is decided by the exact BA-1.1 test: a module is a TCB member if and only if BA-1.1 evaluates true for it.
- BA-1.1's failure semantics: if the test evaluates false for a claimed TCB member, a stated guarantee (typically an integrity, tenancy, or non-interference guarantee) is falsified. That is the whole point of the test — a deterministic instrument to detect when the claimed TCB has drifted.

### §G.2 · Member table reconciliation against `tcb_enumeration_v1`

The TCB member table (currently landed as `TCB.yaml` at the code-repo root · M13-W1 seal) is **reconciled against `tcb_enumeration_v1`**. Any row that appears in `TCB.yaml` but not in `tcb_enumeration_v1` (or vice versa) is a reconciliation defect. This reconciliation happens at the next TCB-boundary CP (post-M12b-W1 · exact CP to be named by the owner).

### §G.3 · SER additions (Solva frame, Northena run loop) enter only via `tcb_enumeration_v1`'s method

The SER may propose additions to the TCB member table (e.g. adding the Solva frame or the Northena run loop as TCB members). Such additions enter the canonical TCB **only through `tcb_enumeration_v1`'s own method** — never as a unilateral SER change. If `tcb_enumeration_v1` does not accept the addition, the SER's proposal does not land.

**Rationale.** This preserves the direction-of-authority from R-18 Part 1: canon > SO > SER > schemas > code. The SER cannot amend the canon TCB enumeration; it can only propose, and `tcb_enumeration_v1` decides.
