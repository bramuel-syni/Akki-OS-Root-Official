## §0 · How to read this file

Each row names ONE mechanism. Columns:

- **`#`** — sequence number, monotonic.
- **`Mechanism`** — the short name we use in commit messages / grounding briefs.
- **`Purpose`** — what it prevents from happening; what it enables.
- **`Where recorded`** — the authoritative source (SO section / DECISIONS entry / CP note / test file).
- **`Introduced`** — the boundary at which it entered force (ratifying commit or ruling turn).

The ledger is a *pointer* to authority, not the authority. If this file drifts from its source, the source wins — always.

## §2 · Regeneration protocol (R-6 fold-in)

This ledger regenerates whenever `ORCH_BOOT.md` regenerates. Concretely:

- **Trigger (a) · Commit-C fixup of any §3.3 3-commit seal:** update `Version`, `Boundary reference`, and — if any new shaping mechanism landed in the seal — append a new row.
- **Trigger (b) · Any owner ruling mutating ratchet / HEADs / STATE:** same as (a).
- **Trigger (c) · Boot ritual detects drift:** regenerate from source (SO / DECISIONS / CP notes) and re-bank; treat divergence as a right-reason RED for the boot verification.

**Append-only discipline.** A row's fields are edited only under one condition: when the mechanism is SUPERSEDED, a new "SUPERSEDED-BY" note is appended to the row, pointing at the successor row's `#`. The original row text is preserved.

**Ownership of authority.** Every row in §1 points at an authority in SO / DECISIONS / CP notes / test files. If this ledger disagrees with the authority, the authority wins and the ledger is corrected — never the rule.

## §3 · How to use this ledger during a long autonomous run

1. At every seal boundary, `check_in` the ledger with `ORCH_BOOT.md` regen (S-07).
2. At every context rollover / new-shift start, read this ledger FIRST after SO — it is a compressed pointer atlas to every discipline currently in force.
3. When adding a new shaping mechanism (e.g. a new invariant test, a new SO clause, a new custody rule), append a row here in the SAME seal boundary that lands the mechanism. Never later.
4. When landing a ruling that supersedes a prior mechanism, append a SUPERSEDED-BY note to the superseded row and add a new row for the successor.
5. When a boot ritual detects that the live authority does not match this ledger, treat the ledger as stale and regenerate it from the authority. Never treat this ledger as authoritative in itself.
